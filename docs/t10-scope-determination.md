# T10 범위 확정 — FR-SBX-01 해석과 Claude Code 분리

확정일: 2026-08-22. 판단 주체: 명세 소유자([H]). 계기: T10-6 정지(`BLOCKED.md`).

## 1. 무엇을 물었나

T10-6 조립 시점에 드러난 사실 — 컨테이너는 뜨지만 **에이전트가 그 안에 없다.**
`claudecode`는 `procgroup.Start()`로 Claude를 호스트에서 실행하고, world lease의
`AdapterEndpoint()`에는 process broker가 아니라 승인 broker가 배선돼 있다.

이 상태로 §8-4를 충족할 수 있는지, 그리고 FR-SBX-01을 달리 해석할 여지가
있는지를 검토했다.

## 2. §8-4는 문면상 충족 가능하나 의미가 없다

§8-4는 "allow 리스트 밖 도메인 접근이 차단되고 `collector/egress`에 기록된다"만
요구한다. 컨테이너에 무언가를 넣고 금지 도메인을 시도시키면 통과한다.

그러나 에이전트가 호스트에 있으면 **에이전트의 실제 egress는 컨테이너 네트워크의
통제를 전혀 받지 않는다.** 테스트는 "컨테이너가 나갈 수 없다"를 증명할 뿐
"서브에이전트가 나갈 수 없다"는 아무것도 증명하지 않는다. 통과가 곧 거짓 신호가
되므로 이 경로를 택하지 않는다.

## 3. FR-SBX-01에 해석의 여지는 없다

명세가 같은 것을 세 곳에서 독립적으로 말한다.

| 위치 | 문구 |
|---|---|
| §2 아키텍처 | 실행 플레인(**샌드박스 안의** 서브에이전트들) |
| FR-SBX-01 | 서브에이전트는 OCI 컨테이너 안에서 실행되어야 한다(**MUST**) |
| FR-ADP-10 | **에이전트 본체만 샌드박스 안에서** 실행된다(**MUST**) |

호스트 실행을 허용하는 독법이 없다. 따라서 이것은 해석 문제가 아니라 범위
문제다. 명세는 개정하지 않는다.

## 4. 문제를 다시 자른다 — 기판과 어댑터는 분리된다

§8-4 통합 테스트는 `claude`를 필요로 하지 않는다. 승인된 제안서 §6이 이미
"CI가 정적 test helper를 빌드해 `FROM scratch` OCI image로 만든다"고 정했다.

즉 **와이어 프로토콜을 말하는 실제 서브에이전트를 컨테이너 안에서 돌릴 수 있다.**
Fake가 아니라 실제 컨테이너의 실제 프로세스다. 그러면 overlay upper에 실제 쓰기가
쌓이고, egress가 실제로 프록시를 거치고, 승인 relay가 실제 경계를 넘는다.
FR-SBX-01·02·03의 **기제가 실물로 증명된다.** 자격증명은 여기 어디에도 걸리지
않는다.

Claude Code가 에이전트를 컨테이너에서 돌리는가는 world 기판 문제가 아니라
**어댑터 문제**(FR-ADP-09/10)이며, 첫 관문은 자격증명이다.

## 5. 확정

**T10 = world 기판을 실제 컨테이너 서브에이전트로 끝까지 검증한다.**

- 통합 테스트의 컨테이너 안 프로세스는 **실제 서브에이전트**여야 한다. 파일을
  쓰고, 금지 도메인에 시도하고, 툴 승인을 요청한다. 껍데기를 넣고 통과시키지
  않는다.
- 미충족을 정확히 기록한다. **"T10 완료"는 "샌드박스 완성"이 아니다.**
  production Claude Code 경로는 에이전트가 호스트에서 실행되므로 그 어댑터에
  대해 FR-SBX-01은 미충족이다. 추적 매트릭스에 별도 행으로 남긴다.

**Claude Code의 sandbox 실행은 T15로 분리한다.** 착수 조건은 자격증명 경로의
[H] 실측이다.

## 6. 자격증명 — 지금 고르지 않는다

FR-SBX-04는 단기·좁은 스코프 토큰을 MUST로 요구하고 장기 자격증명의 컨테이너
반입을 MUST NOT으로 금지한다. T9에서 확인한 Claude Code의 인증 경로는:

| 경로 | FR-SBX-04 |
|---|---|
| OAuth/Keychain | 호스트 결속. 실측(2026-08-19): `CLAUDE_CONFIG_DIR` 이전 시 `authentication_failed` |
| `ANTHROPIC_API_KEY` | 장기 자격증명 — MUST 위반. T9에서 이미 미승인 |
| `claude setup-token` | help 원문이 "long-lived" — 장기 |
| Bedrock/Vertex/Foundry | `--bare` help가 "3P providers use their own credentials". AWS STS는 단기·스코프 한정 — **문면상 유일하게 적합** |

마지막 경로가 실제로 되는지는 **실측 없이 판단하지 않는다.** 이 프로젝트에서
문서만 보고 내린 판단이 세 번 뒤집혔다: T9 init 순서(픽스처 8/8이 근거였고
틀림), Keychain과 `CLAUDE_CONFIG_DIR`의 독립성(문서적으로 맞고 실제로 틀림),
bind mount의 워크스페이스 격리(자명해 보였고 실측이 반증). T15 착수 전에
T9 smoke와 같은 [H] 실측을 수행한다.

## 7. 즉시 진행

1. `process broker` + `Open → spawn ACK → Start` 분리 재제안 (모든 선택지에서 필요)
2. 그 위에 컨테이너 test 서브에이전트로 §8-4 통합 테스트
3. T15는 자격증명 [H] 실측을 착수 조건으로 대기
