## 2번의 잔여 — 컨테이너 안 실 토큰 Claude 세션

2b는 어댑터 충실성 + child span 기록이며 위 증거로 충족된다. 이와 **별개로**
FR-SBX-01의 "Claude 본체가 샌드박스 컨테이너 안에서 실행"은 다음 상태다:

- **기제는 배포 커널(Linux CI)에서 증명됨.** `t15-linux-gate` 5-attempt matrix가
  무자격증명으로 관통: 컨테이너 안 Claude 기동·ProcessEndpoint
  stdio·overlay·egress·승인 relay·토큰 없는 인증 실패 `done{error}`·토큰 미유출.
- **미실행:** 실 토큰으로 인증된 Claude가 컨테이너 안에서 성공한 tool call을
  내는 끝-대-끝 한 장면. 하네스·runbook 완비(`t15_smoke_test.go`,
  `t15-smoke-runbook.md`)이나, 토큰(로컬)과 배포 커널(Linux)이 같은 머신에
  있어야 하고 이 조건이 현재 개발 환경에 없다.
- **macOS VM은 대표 실행 불가.** podman machine이 호스트 경로를 공유하지
  않아(MOUNTS:0) 바인드 마운트가 성립하지 않는다 — VERIFICATION이 아닌
  INFRASTRUCTURE 한계(블로커 기록, 비공개). 또한 macOS VM은 배포 커널을 대표하지
  않으므로 제안서(§Q4)가 처음부터 보조 증거로 격하했다.

이 잔여는 **정상 사용자 환경(리눅스 호스트)에서 자연히 충족된다.** control
plane 조작은 어디서나(macOS 포함) 가능하고, 에이전트 격리 실행은 리눅스
호스트에서 한다 — 명세 §2의 control/execution plane 분리 그대로다.

## FR-SBX-04 — 현행 위협 모델에 맞춘 개정 결과

명세 소유자가 2026-10-06 SCP-SBX04-001 선택지 A를 승인했다. 컨테이너는
벤더 자격증명을 받지 않고, JANUS 밖 운영자 게이트웨이의 접근키만 받는다. 접근 가능한
목적지는 FR-SBX-03 정책 allowlist와 선언된 egress 핀으로 제한된다. 명세는 접근키 값이
argv·spawn 메타데이터·이벤트 로그·출력 스트림에 남지 않아야 한다고 요구한다. 현행 판정은
T29에서 argv·spawn 메타데이터 부재와 Claude 경로(ANTHROPIC_AUTH_TOKEN/
ANTHROPIC_API_KEY), Codex OPENAI_API_KEY 컨테이너 stdout/stderr 및 승인 요청
(subagent/approval/request args·raw) 정확값 마스킹을 writer 경계(fake launcher가 approval
request를 Submit) 테스트로 충족했다 — claudecode approval_socket→writer 실경로는
단일 writer 초크포인트로 갈음한다.
짧거나 일반적인 값은 config에서 거부하고 `redaction_patterns`를 지원한다. 게이트웨이 키
egress 제한은 FR-SBX-03 allowlist·핀 테스트로 간접 근거를 둔다. 벤더 자격증명 비취급은
생산 경로가 벤더 토큰을 발급·보유하지 않고 CLAUDE_CODE_OAUTH_TOKEN을 거부하는 것
(TestWorldConfigEnvironmentErrorsDoNotEchoValues)까지 기계 검증되며, world-config env
값이 게이트웨이 키인지 벤더 키인지는 JANUS가 판별하지 않는다(운영자 책임). 이 판정은
`surfaces/hx/run_production_gateway_test.go` (`TestWorldConfigGatewayEnvironment`,
`TestWorldConfigEnvironmentErrorsDoNotEchoValues`), `seams/world/local/environment_test.go`
(`TestGatewayAccessKeyEnvironmentAndRedaction`), `seams/world/local/egressproxy/pins_test.go`
(`TestPinnedDomainSkipsDNSAndDialsPinnedAddress`, `TestPinnedConnect443DialsPinnedAddressWithoutDNS`,
`TestPinnedDenialsNeverDialAndAreAudited`) 및 allowlist 테스트로 근거를 둔다.

> **각주 (2026-10-06):** 명세 개정(SCP-SBX04-001)과 T29 구현으로 컨테이너 생산 경로의
> 내장·secret_env·휴리스틱 secret literal이 스트림·이벤트 payload/raw·제어 출력에서 마스킹된다.
> 짧은 값은 claim 전에 거부된다. world-config env 값이 게이트웨이 키인지 벤더 키인지는
> JANUS가 판별하지 않으며, host 모드는 비범위이고 구독 OAuth env 이름은 계속 거부한다.

## 결론

작성 시점(2026-09-06)의 v0.1 릴리스 게이트 여덟 기준 중 **여섯은 완전 충족**이었다. 2번은 두 부분으로
갈린다: Claude는 골든·실 세션·컨테이너 기제(Linux CI 5회)까지 완전, 남은 것은
컨테이너 실 토큰 세션 한 장면(위 §2 잔여)이다. **Codex 실 세션 잔여는
traceability T16-3의 PASS로 해소되었다.** (호스트 모드 — 컨테이너 밖
macOS 로컬 실측, ApprovalAuto; 컨테이너 안 codex 실행은
traceability T16-3 행의 잔여.)

남은 잔여는 코드·설계 결함이 아니라 Claude 실 토큰의 범위·환경 문제다. 실
토큰은 리눅스 호스트 사용자가 runbook으로 확인한다. Codex 상태는 위 traceability
기록을 따른다.
